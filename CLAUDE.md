# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## Project

A native macOS download manager (Free Download Manager–style): multi-connection downloads, SwiftUI app, no browser integration. Decisions made: macOS 15 minimum, direct notarized distribution, App Sandbox off, custom URL scheme `fetchthings://` (must open a prefilled Add sheet, never start a download silently). Out of scope, but the engine should stay open to them: browser integration, torrents, yt-dlp.

**Name:** the app is **FetchThings** (it was "Downloader" until the rename; the repository is `FetchThings`). Only the app carries that name: the engine package stays `DownloadKit`, and its `Downloader` protocol, `SegmentedDownloader` and `SingleDownloader` are unrelated words for "the thing that transfers bytes", so a search for "Downloader" still finds them (do not rename them). The rename changed the bundle id (`com.example.FetchThings`), so job files, settings and Keychain items saved by an old `com.example.Downloader` build are not read by the new one.

**Current state:** Phases 1 and 2 are done: the engine (`DownloadKit/`, a local Swift package) and the SwiftUI app (`App/`, generated Xcode project) with Liquid Glass styling, speed modes and English/Turkish localization. Phase 3 is not started: menu bar extra, Dock badge/progress, Notification Center alerts, scheduling, launch at login, polish. The app icon is done: `FetchThings.icon` in the repository root, an Icon Composer document (a down arrow through a hoop: three SVG layers, the arrow a Liquid Glass layer, on the system-light fill), edited with Icon Composer (inside Xcode.app, `Contents/Applications`). `project.yml` lists it as a source (XcodeGen adds it as one `wrapper.icon` resource) and sets `ASSETCATALOG_COMPILER_APPICON_NAME: FetchThings`; actool compiles it into `Assets.car` (the layered icon macOS 26 draws, including the Dark, Clear and Tinted looks) and, because the deployment target is macOS 15, into a flat `FetchThings.icns` (16, 32, 128 and 256 px only, which is what actool emits) for older systems. Change the icon by editing the file, nothing else. It replaced a PNG `AppIcon.appiconset` (a magnet and a document) rendered from `Design/AppIcon.svg` and `Design/AppIcon-small.svg`; those two files and the handoff zip are the old design and unused. To see the result, look at the running app's Dock icon: `NSWorkspace.icon(forFile:)` returned the same grey image whatever appearance was asked for, and Quick Look on a `.icon` hangs in a command-line session. The Dock follows the Mac's icon style (Default, Dark, Clear, Tinted), so check which one is set before judging colours. **A build that already existed at a path keeps showing a generic placeholder icon in the Dock after the icon is added or changed** (seen with the Xcode build in DerivedData: identical bundle contents showed the icon from a new path and the blank placeholder from the old one; `lsregister -f` did not help). The system's icon cache is keyed on the modification date of the `.app` folder itself, which incremental builds leave alone: `touch` the `.app` (or Clean Build Folder), then run it again. The bundle id `com.example.FetchThings` is a placeholder and builds are ad-hoc signed; the user must set a real id, `DEVELOPMENT_TEAM` and a Developer ID before distributing (Release already enables the hardened runtime). **Release tags track the Apple OS/Xcode version this build targets, not semantic versioning** (`v27.0` for this Xcode 27 beta cycle, not `v1.0.0`): `.github/workflows/release.yml` triggers on `v*.*`, pinned to the `xcode-27` runner to match; bump both together when the project moves to a newer Xcode. Phases: (1) engine + tests, (2) main UI, (3) menu bar, scheduling, polish. After each phase: build, run tests, then `/code-review` and `/simplify`; run `/security-review` before finishing; report honestly what was and wasn't tested.

## Commands

All engine work happens in `DownloadKit/` (Swift 6 language mode, Xcode 27 / Swift 6.4; `Mutex` needs macOS 15). No linter or formatter is configured.

```bash
cd DownloadKit
swift build --build-tests          # library + tests; the library builds with zero warnings, keep it so
swift test                         # whole suite, ~45 s (the limiter tests sleep)
swift test --filter DownloadIntegrationTests                 # one suite
swift test --filter resumesFromTheByteWhereAConnectionDropped # one test (matches the function name)
swift test --skip-build --filter <name>                      # re-run without rebuilding
```

Tests use Swift Testing (`@Test`, `#expect`), not XCTest.

The app is an Xcode project **generated by XcodeGen** from `project.yml` (installed via Homebrew). Edit `project.yml`, not the `.xcodeproj`, and re-run `xcodegen generate` whenever files are added or removed under `App/` or `AppTests/`.

```bash
xcodegen generate
xcodebuild -project FetchThings.xcodeproj -scheme FetchThings -destination 'platform=macOS' build
xcodebuild -project FetchThings.xcodeproj -scheme FetchThings -destination 'platform=macOS' test
xcodebuild ... test -only-testing:FetchThingsTests/AppModelTests   # one suite
```

Add `-derivedDataPath <dir>` to keep build output out of `~/Library`. After deleting or renaming a file under `App/` or `AppTests/`, run `xcodegen generate` again before building: the committed project lists files explicitly, and a stale one fails to build (or worse, runs a stale test bundle). The app tests are hosted inside the app and print harmless `linkd ... autoShortcut` connection errors; ignore them.

## Engine architecture (`DownloadKit/Sources/DownloadKit`)

Data flow: `DownloadManager` (actor: queue, concurrency cap, global limiter, persistence, event stream) owns one `DownloadJob` (actor) per download. A job runs probe → transfer → verify → finalize and reports `JobReport`s back through a closure. The transfer itself runs in non-isolated tasks and is only *sampled* by the job's tick loop (about 4 Hz), never driven per chunk.

- **One connection is the 1-segment case.** `TransferMode.segmented` (server gave a size and honors ranges) uses `SegmentedDownloader` + `SegmentScheduler`; `.single` uses `SingleDownloader` (plain GET, not resumable, restarts from zero). A server that advertises ranges but answers 200 makes the job throw `rangeNotHonored` and fall back to `.single`; a changed ETag/size makes it throw `resourceChanged` and restart (max 2 times).
- **`SegmentTransfer` = one request, one `URLSession`.** A session per transfer is deliberate: over HTTP/2/3, requests sharing a session are multiplexed onto one TCP connection, which would silently defeat multi-connection. Chunks are `pwrite`n from the delegate queue straight into the shared `PartFile` (no actor hop). Speed limiting stalls a request by suspending its `URLSessionDataTask`, **but that alone barely limits anything**: URLSession reads several megabytes ahead of a stall (about 4 MB per connection; with 8 connections 35 MB, most of a 48 MB file, arrived in three seconds under a 1 MB/s limit), and a stall cannot hold back a request that has already finished. So while a limit is active, `SegmentedDownloader.download(segment:)` (a) asks for each segment in pieces of at most `RateLimiting.maxRequestBytes` (a quarter second of traffic at the current rate, clamped to 128 KB...4 MB), which bounds the read-ahead, and (b) waits out `pendingDelay()` before starting the next piece (`RateLimiting.waitUntilClear`, which reads the debt again every 0.25 s; a stalled request does the same in `SegmentTransfer.scheduleResume`), or the pieces would replace each other instantly and bypass the limiter. Sleeping out the whole debt in one go left every connection idle for minutes after the user raised a very low limit or picked High. Each piece is its own request with its own `URLSession` and its own `If-Range`: that is a new connection per piece, and a server whose nodes give the same file different ETags can make a piece answer with another ETag and the job restart as `resourceChanged`; not seen in practice, so not mitigated, but it is the first thing to check if a limited download of a big file from a CDN keeps restarting. No limit means whole-segment requests as before. A piece that ends early is treated like an interrupted attempt (`prepareAttempt` resumes from what is committed, and progress resets the retry budget). A `.single` download (no range support) cannot be paced this way and keeps the old, looser behaviour. Measured through the app: a 50 MB file took 48 s at 1024 KB/s (1.04 MB/s), 12.5 s at 4096 KB/s and 0.8 s unlimited.
- **`SegmentScheduler` invariant (the core of resume correctness):** per segment, `received` (committed, on disk, the only value persisted) trails `reserved` (a write cursor). Workers `reserve → pwrite → commit`. Work stealing (an idle slot splits the segment with the most unreserved bytes left) only takes bytes beyond `reserved`, so no byte is written twice. Resume points always come from `received`. `SegmentedDownloader` counts an attempt against the retry budget only if the segment made no progress.
- **Probe (`Prober`):** HEAD first; range support is only believed after `Accept-Ranges: bytes`, otherwise a `Range: bytes=0-0` GET settles it (HEAD is often rejected, and many servers honor ranges without saying so). Requests send `Accept-Encoding: identity`; any `Content-Encoding` disables ranges and drops the size.
- **Manager ordering rules** (`DownloadManager.handle`): update the snapshot, broadcast, and hand the record to the store *before the first suspension*, so a job's reports keep their order. `runningIDs` is mutated synchronously before `await job.start()` so concurrent `scheduleNext()` passes can't exceed the concurrency limit; `start()` returns `false` if the job is no longer queued and the manager then gives the slot back. The manager's snapshot can lag the job, so `pause()` never trusts it: it calls `job.stop(to: .paused)`, which handles running, starting and queued jobs. After `shutdown()` nothing may start (`isShutDown`), otherwise a job stopped back to `.queued` is immediately restarted.
- **Secrets that cannot be read fail the download.** `DownloadRecord.hasSecrets` remembers that a download was added with cookies, headers or credentials; if the `SecretStore` cannot return them later, the job fails with `credentialsUnavailable` before any request, instead of downloading unauthenticated (which could save a login page as the file).
- **Job persistence:** one JSON file per download (`FileJobStore`, dir 0700, files 0600), checkpointed every `checkpointInterval` and on every state change. On `load()`, records left in a running state go back to `.queued` (auto-resume). Removing an unfinished download always deletes its `.part` file.
- **Never trust saved progress blindly.** The `.part` file is preallocated to full size, so its length says nothing about what is in it. A resume only keeps progress if `SegmentPlanner.isValidPlan` accepts the saved segments (a bad list would otherwise trap in `SegmentScheduler.init`) and the part file's size equals the total; otherwise it restarts. Completion is checked by counting received bytes, not file size. Checkpoints snapshot the counts *before* `fsync`ing the part file (`Downloader.flush`), so a checkpoint may lag the disk but never lead it. A `.single` download has nothing to resume (`downloadedBytes` is 0 until completed).
- **Errors:** `DownloadError.isRetryable` decides retry vs fail (408/425/429/5xx except 501/505, and transient `URLError`s retry; other 4xx, disk, checksum, path errors don't). `DownloadError.map` turns `URLError.cancelled` into `CancellationError`, which means "stopped by caller", never "failed".

## App architecture (`App/Sources`)

- **`AppModel`** (`@MainActor @Observable`) is the single source of truth for the window. It talks to the engine only through the `DownloadEngine` protocol (`DownloadManager` conforms; tests use `FakeEngine`). A task that is *not* on the main actor drains the engine's event stream into `EventInbox` (newest event per download, lock-protected), and the main actor applies it every 200 ms (`flushEvents`). That bounds memory whatever the UI is doing and keeps the views from refreshing on every progress tick. `visibleDownloads` (sidebar filter, search, sort) and the sidebar `counts` are recomputed only when the data or a filter changes.
- **`selection` is always a subset of `visibleDownloads`.** `recomputeVisible` prunes it, and every action (pause, remove, reveal, the toolbar state) works on the visible selection only. Without that, filtering or searching left hidden rows selected and the Remove button deleted downloads the user could not see.
- **Removing goes through `requestRemoval`**, which asks first when it would delete partly downloaded data, or when it would take more than one entry off the list at once (`PendingRemoval`, shown as a confirmation dialog; Select All then Delete used to empty the list with no question and no undo). Removing a single finished or untouched entry does not ask. The app never asks the engine to delete finished files; "Remove and Move File to Trash" calls `FileManager.trashItem` itself (`AppModel.trash`, replaceable in tests). There is deliberately no global ⌘⌫ shortcut (it would fire while typing in a text field); Delete works through `.onDeleteCommand` on the table.
- **Start-up order matters:** `AppModel.start()` (called from `applicationDidFinishLaunching`, not from a view) applies the concurrency and speed limits *before* `engine.load()`, because loading auto-resumes downloads immediately. `onCompleted` fires for a download that finishes during this session even if its whole life fell between two refreshes; ones restored as already finished do not fire it.
- **Numbers typed by users are clamped** (`SpeedLimit`, `AppSettings`): KB/s x 1000 overflowed `Int64` and crashed on every launch when a huge value was persisted. `AppSettings` keeps its own numbers in range in their `didSet`s, so any writer (a Settings field now, a menu bar item or a schedule later) is covered; the put-back is guarded by `!=` because under `@Observable` every assignment, of the same value too, runs `didSet` again and an unguarded one recursed until the stack overflowed (the app tests crashed on it).
- **Links from outside only propose downloads.** `fetchthings://add?url=…`, dropped or opened `.txt` files, dropped or pasted text, Services and clipboard offers all end in `presentAddSheet`, and only the sheet's Add button calls the engine. Keep it that way: any web page can trigger a `fetchthings://` link. Non-http(s) links are filtered by `LinkParser` (and `IncomingLinks` for files).
- **Single `Window` scene, not `WindowGroup`**, so opening a link or file with the app does not spawn another window. Closing that window leaves the app running with the window retained but hidden, and SwiftUI then reports `canBecomeMain == false` for it, so `MainWindow.showIfHidden` finds it by its scene id (`MainWindow.sceneID`, exposed as `MainWindow.window`, which Quick Look and the search field also use to reach their AppKit views through `NSView.firstDescendant`) and is called for link opens, Dock reopen and the Services item; otherwise the Add sheet (which lives in that window) would be invisible. URL and file opens arrive in `AppDelegate.application(_:open:)`, which is also where Dock-icon drops land; text cannot be dropped on a Dock icon, so the "Add to FetchThings" Service (`NSServices` in `project.yml`, `ServicesProvider`) covers it. `AppDelegate.applicationShouldTerminate` stops the transfers (`AppModel.shutdown`) before quitting, but `TerminationGate` gives up waiting after 8 seconds so a stuck shutdown cannot block quitting.
- **Storage:** job files in `~/Library/Application Support/<bundle id>/Jobs`, secrets in the login keychain (`KeychainSecretStore`), preferences in `UserDefaults` (`AppSettings`, values clamped on load). When the app hosts unit tests (`AppEnvironment.isRunningTests`) it uses a temp job folder, an in-memory secret store and a throwaway defaults suite, so tests never touch real data. Setting `FETCHTHINGS_SANDBOX=<folder>` does the same for a hand- or script-driven run (jobs in `<folder>/Jobs`, downloads in `<folder>/Downloads`, secrets in memory, settings in a suite that is reset at launch; `FETCHTHINGS_APPEARANCE=dark|light` forces an appearance in that mode).
- `Info.plist` (generated from `project.yml`) carries the pieces that must stay in sync with code: the `fetchthings` URL scheme, `NSAllowsArbitraryLoads` (plain http downloads), the `.txt` document type and the Services entry.
- The clipboard watcher is opt-in and uses `NSPasteboard.detectedPatterns` (macOS 15.4+) to check for a web address *without reading the contents*, then reads only on a match; before 15.4 it reads directly.
- **The details pane is a floating Liquid Glass card of fixed width in a plain `HStack` (`MainView`), not `.inspector`, and starts hidden (`showInspector = false`).** `.inspector` inside the `NavigationSplitView` detail crashed the app with `NSGenericException: The window has been marked as needing another Update Constraints in Window pass...` (an AppKit layout loop that hangs the UI for seconds, then aborts) when the window was at its minimum width and the pane was toggled; an `HSplitView` avoided the crash but centred the table vertically and overflowed the window when the pane opened (sidebar clipped, toolbar collapsed into `»`). The widths that must add up live in `MainWindowLayout`: sidebar max 250 + table min 320 + pane 272 + 2 x 8 margin = 858 <= `minWindowWidth` 860. If you change any of them, check the window at its minimum width with the pane open (screenshot) and re-run the Accessibility stress test (see "Verifying UI work"); a unit test cannot see this. The pane toggle is a `Button`, not a `Toggle`: a toolbar `Toggle` reaches VoiceOver with no title or description.
- **"A finished file" is `DownloadSnapshot.completedFileURL`** (`finalURL` once the state is `.completed`); `AppModel.availableFile` adds the check that it is still on disk. The engine only reports a `finalURL` for a completed download, so the state check only guards a snapshot built by hand (one test does, on purpose).
- **The details pane shows what the file looks like, as Finder does** (`FilePreview.swift`). `DownloadPicture` draws a Quick Look thumbnail of a *finished* file (a video frame, a photo, a PDF's first page; `FileThumbnails` uses `QLThumbnailGenerator` with `.thumbnail`/`.lowQualityThumbnail` only) and the type icon (`FileIcons`) while it downloads or when the system has no preview for that kind of file (a `.dmg`). Several selected downloads become `DownloadStack`: up to four pictures fanned out, the first on top, with a count badge. Thumbnails are cached (an `NSCache` of 100) per path + modification date + size; the date is read with `FileManager.attributesOfItem`, not `URL.resourceValues`, because a `URL` object caches what it read and would keep the old date after a file is replaced (a unit test found this). The picture in the pane is `.id(download.id)`: without it its `@State` outlived a change of selection, so arrowing through files flashed the icon before each thumbnail, and a preview made for one version of a file could be shown after the file was replaced. Real files are needed to look at it: the mock server's random bytes have no preview.
- **Finished files can be dragged out of the list, and Space opens Quick Look** (both in `DownloadTable`). The table is `Table(of:rows:)` so each row is a `TableRow` with `.itemProvider { model.dragProvider(for:) }`: an `NSItemProvider` holding the file's URL, or nil (row not draggable) unless `AppModel.availableFile(of:)` finds a completed download whose file is still on disk. Dragging several selected rows carries all of them. The source offers copy only, so Finder copies and never moves the download out from under the list. SwiftUI itself clones every dragged file into `~/Library/Caches/com.apple.SwiftUI.Drag-<uuid>/` and hands receivers that path (instant and free on APFS, measured with a 1 GB file; `NSItemProvider(contentsOf:)`, a data representation and a plain URL all end up there) and never removes it, so those clones pile up: not ours to fix, but delete them by hand after testing. **The details pane avoids all that**: the big picture (`DownloadPicture`) and the pile of several selected files (`DownloadStack`) are dragged with `FileDragSource` (`FilePreview.swift`), an `NSViewRepresentable` overlay whose `NSView` starts a real `NSDraggingSession` with one `NSDraggingItem` per file (`NSURL` writers, `.pile` formation, copy-only mask, the first four pictured by their preview or icon under the pointer). SwiftUI's `onDrag` carries a single item, so it could not drag a pile at all; the AppKit session hands receivers each file's own path and makes no cache clone (checked with the drop probe: 1 and 3 originals, no `com.apple.SwiftUI.Drag-*` folders). Space is `.onKeyPress(keys: [.space])` on the table (Option-Space = full screen), so it only fires while the table has focus, never while typing in the search field; ⌘Y and a context-menu item do the same from the menu (the menu item first makes the right-clicked row the selection if it is not part of it, as Finder does, because Quick Look shows the selection and SwiftUI leaves it alone on a right-click). `QuickLookController` runs the shared `QLPreviewPanel`, and **must get control through the responder chain**: `AppDelegate` implements `acceptsPreviewPanelControl`/`beginPreviewPanelControl`/`endPreviewPanelControl` and hands the panel to the controller. Setting `panel.dataSource` directly worked but made Quick Look log "called while the panel has no controller" and skipped the open/close zoom. With one file showing *and one row selected*, the arrow keys in the panel move the list selection (`previewPanel(_:handle:)` → `AppModel.moveSelection`, then `scrollRowToVisible`); with several the panel pages by itself. The zoom animation needs the row's screen frame, so the table is marked `.accessibilityIdentifier(DownloadTable.accessibilityID)` and found in the window's AppKit views (`QuickLookController.findTable`). The panel follows the selection (`onChange(of: model.selection)` in `MainView`) and closes when the selection has no finished file.
- **The window refuses drags that started in this app** (`OwnDrag`, `IncomingDropDelegate`). The whole window is a drop target for links, `.txt` files and text (`.onDrop(of:delegate:)` in `MainView`), so a file dragged out of the list or the pane and dropped back on the window (the natural way to cancel) used to be read as a file of links and end in a "No Links Found" alert. Every drag out of the app carries a mark type (`OwnDrag.identifier`): rows through `AppModel.dragProvider` (a data representation with `.ownProcess` visibility), the pane through `DragSourceView.pasteboardItem`; `validateDrop` returns false when the mark is present, so the drag slides back with no alert. Reproduced by turning the check off (the alert appears) and fixed by turning it on, with the scratch drag source and drop probe. When reading what was dropped, judge each item by its real type (`hasItemConformingToTypeIdentifier(UTType.url…)`), not by `itemProviders(for: [.url])` or `canLoadObject(URL)`: `NSURL` can also *read* plain text, so a text drag counted as a URL drag and produced a "no links" alert for text that held links. A drop delegate replaced two `dropDestination`s because those cannot inspect what is being dragged before accepting it.
- **The toolbar search field is hand-made and as wide as the details card** (`ToolbarSearchField.swift`, `SearchFieldLayout`), not `.searchable`. In dark mode the table and the area around the card are different greys, and the system's search field, as wide as the toolbar leaves room for (about 325 pt), straddled that edge. What was tried first and why it was dropped: the field cannot be given a width through SwiftUI; setting `preferredWidthForSearchField` on the `AppKitSearchToolbarItem` (an `NSSearchToolbarItem`, added a second or so after launch, and `NSToolbar.willAddItemNotification` is not posted for SwiftUI's toolbar) changed nothing, and lowering the max-width constraint of its `NSSearchToolbarItemView` plus hiding and re-showing the item did narrow it, but SwiftUI reset it to 325 on the next relayout. So the field is a SwiftUI view in a `ToolbarItem`. Things that had to be handled: (1) toolbar items placed together are merged into one glass capsule (the field used to sit beside the buttons), so the field opts out with `.sharedBackgroundVisibility(.hidden)` (macOS 26) and draws its own `glassSurface(.capsule)`; (2) a toolbar does not shrink an item to fit, and at the minimum window width the field was pushed into the toolbar's "»" overflow menu (a flexible `frame(minWidth:maxWidth:)` made no difference), so `SearchFieldLayout.width` works its width out from the detail area's width (`onGeometryChange` in `MainView`) less an estimate of the title and buttons (`otherToolbarItems`, 500 pt; the subtitle grows with speed and active count, so this is an estimate) with a 120 pt floor; (3) a toolbar item is hosted apart from the window's content, so a `FocusState` in `MainView` cannot focus a field inside it: the field owns its focus and `model.isSearchFocused` is a request it acts on (⌘F), and setting the field's own `FocusState` was still not enough (the table kept focus), so it also finds the `NSTextField` among the toolbar items' views (`ToolbarSearchField.focusFieldInWindow`; the SwiftUI accessibility identifier is not on the NSView) and calls `makeFirstResponder`. Verified with the accessibility API (`AXFocusedUIElement`): ⌘F focuses it, typing works, the clear button clears, Escape clears then hands focus to the table, and a click in the table takes it back. It also has the clear button, Escape (clears, then gives focus back to the table) and the search role for VoiceOver, which `.searchable` used to provide. **The buttons are in the toolbar's leading side** (`ToolbarItemGroup(placement: .navigation)`, right of the sidebar toggle, before the title), not trailing beside the search field. Trailing, their capsule ended right where the table meets the strip around the details card, and crossed that edge as soon as the search field shrank in a narrower window (each point it gave up pushed the capsule a point further right); at the minimum window width it could not be avoided. Leading, they are hundreds of points from the edge at every supported width, and only the search field sits above the card. Things tried for the colour step itself, all abandoned because it is different on each Mac (macOS tints the window background; on the reporter's Mac the table side measured 52,52,54 against 41,41,45 beside the card, on the development Mac the two were within 2 units): `.scrollContentBackground(.hidden)` on the `Table` does nothing; clearing the `NSTableView`, its clip view and scroll view backgrounds did nothing (the table already shows what is beneath it); painting the strip with `Color(nsColor: .controlBackgroundColor)` made it worse (a neutral grey against the table's blue-grey). Sampling pixels of a screenshot (`px <png> x y`) beats guessing at colours. **A bug that looked like a toolbar quirk**: right after launch the toolbar was laid out wrongly (buttons about 150 pt and the field about 76 pt too far right, the field partly outside the window under the buttons; a resize fixed it). Cause: the first `onGeometryChange` reading is taken before the layout has settled and came out tiny, so the field's width state briefly held the 120 pt floor; the toolbar reserved a slot of that width and never re-measured it when the field grew back to 272 (only a window resize makes it). The clue was arithmetic: the space right of the buttons was 124 pt, the floor plus the gap. `SearchFieldLayout.width` therefore ignores any area narrower than the window can really be (`smallestRealArea`) and answers the widest width. If a toolbar item ever sits in the wrong place after launch, look for a size that changed after the first layout.
- **One design language, no decoration** (`GlassComponents.swift`): the Add sheet, the Settings window and the details pane are all built from the same few pieces: `IconChip` (a tinted glass disc with a symbol), `SettingTile` / `TileSection` (a glass tile: chip, title, optional line, control on the right, under a small caption with an optional note below), `StepperControl` and `StepButton` (round glass − and +), `fieldBackground()` / `insetField(width:alignment:)` (a soft inset for text fields, and the whole one-line field with its padding), `CaptionedField` (a small caption over a control) and, where the surface is already glass (the details pane), `InsetGroup` + `DetailRow` (rows on a 6% inset with hairlines, `Group(subviews:)` interleaves the dividers; a second layer of glass there only muddied it). Use them for any new window instead of a grouped `Form`. Colours mean something: blue folder, purple connections, teal queue, orange clipboard, grey generic, and the speed modes' red, yellow and green (`SpeedMode.color`, also the chips in Settings); state colours come from `DownloadSnapshot.stateTint` (progress bar and status pill). **Do not add gradient or mesh backgrounds** (the Add sheet had an animated `MeshGradient` behind the glass; the reporter found it looked AI-generated and it was removed): glass sits on the system material. The details pane is a scrolling `ScrollView` of `InsetGroup`s under a header (picture, name, a tinted status pill, and for unfinished downloads a glass `ProgressBar` with "x of y · speed · time left"); the old `Form` was replaced.
- **Liquid Glass goes through `Glass.swift`** (`glassSurface`, `glassButton`, `GlassGroup`) because the app still supports macOS 15 and the glass APIs need macOS 26; each falls back to a material or the plain button style. The fallback draws the tint *behind* the content, at the strength the caller chose: as an overlay in front (and at a quarter of that strength) it swallowed every click on the buttons inside a tinted surface (the speed-mode button and rows, the links well's Paste and ✕) and left white glyphs unreadable, which only shows on macOS 15 and was found by hosting the modifier chain in an offscreen `NSHostingView` and sending it mouse events. Glass is used for the progress bars, the links field, the buttons in the Add sheet and Settings, the details pane, the connection map and the clipboard banner; the toolbar, sidebar and table rows get theirs from the system. Two things learned by looking at it: two glass shapes inside one `GlassEffectContainer` blend, so the progress bar's fill lost its crisp end (draw the track and the fill as separate glass shapes); and glass on a plain white sheet has nothing to refract, so the Add sheet uses `.presentationBackground(.regularMaterial)`. Keep glass to controls and floating surfaces, not to every table cell.
- **The Add sheet is a Liquid Glass composition** (`AddDownloadSheet.swift`): a hero header (glass disc, "N links" that counts up), a glass "well" with the link input and a card per link, tiles for the folder (with free space), connections (glass − and + buttons, one adjustable element for VoiceOver) and "add paused", an Advanced tile that **morphs** into its panel (`GlassGroup` + `glassMorph`, i.e. `glassEffectID`, macOS 26 only), on a plain `.regularMaterial` sheet background. **The links field is a token-style input, not a text area**: the text you type or paste is `pending`; links in it become cards (`AddDraft.append`, deduplicated) when a paste arrives (`PasteDetection`: what was inserted holds a whole address, scheme included, or a line break; judging by "more than one character arrived" committed a half-typed `https://exam` whenever two keystrokes landed together), when a line break arrives (⌥↩) or on Return; a card's ✕ calls `AddDraft.remove`; the draft holds an ordered `links: [URL]` (http(s) only, no repeats, at most `LinkParser.maxLinks`), not text that is parsed again on every change; Return on an empty field starts the downloads, Return on text that holds no link shows a note and keeps it; ⌘↩ adds from anywhere, and `add()` first commits a link that was typed but not entered. `add()` refuses to run again while `isAdding` (Return in the field is not disabled the way the buttons are, and a second Return queued every file twice), `isAdding` stays set after success until the sheet is gone, and Cancel/Esc are disabled while adding (Cancel only closed the sheet over an add that went on, and the failure branch then wrote its links into the next, freshly reset draft). The Paste button reads the pasteboard only when clicked. The well is a drop target (`IncomingDropDelegate` with `isTargeted`, which lights it): what is dropped goes through `model.handleIncoming`, which appends when the sheet is already open. (The half-width "Connections" and "Add paused" tiles are hand-laid-out on purpose: built from `SettingTile` and `StepperControl`, "Connections" wrapped to "Connec-tions" and "Waits until you start it" was cut at its front, in English and in Turkish.) **Links that arrive from outside while the sheet is open (`presentAddSheet` with `showAddSheet` true: a `fetchthings://` link, a drop, a file, the Services item) are sent without the cookies, headers and login typed into the sheet** (`AddDraft.linksWithoutSecrets`, `append(_:fromOutside:)`): any web page can trigger a `fetchthings://` link, and it must not be able to borrow what the user typed for another site; the sheet says so under the well when it applies, and a link the user pastes or re-enters themselves is theirs again. When what arrives holds no link, `AppModel.report` puts the message in `sheetNote` for the sheet to show under the well (the sheet takes it with `.onChange(of:initial: true)`: `handleIncoming` sets it right after opening the sheet, before the sheet exists, and an edge-triggered `onChange` never saw it; `resetDraft` clears it) (an alert would sit on the window behind the sheet and appear only after it closed). A failed add names the link without any `user:pass@` (`URL.withoutCredentials`). Cards show `LinkSummary` (`URL.displayFileName`: the last path component decoded once by `URL` and run through `FilenameSanitizer`, so it matches what will be saved and cannot carry a right-to-left override that shows `invoice.exe` as `invoiceexe.pdf`; host; lock; never the password of a `user:pass@` link). Sizing: header and footer are fixed and the middle scrolls, capped by the height of the window the sheet hangs from (`middleLimit`, read from `NSWindow.sheetParent` in `ParentHeightReader`): without that an expanded sheet was 693 pt in a 640 pt window and hung out of it; with a nested scroll view inside a fixed `frame(height:)` the Advanced panel showed two fields. A scroll view clips glass at its edge, so the content is padded 6 pt and the scroll view widened by the same; `.scrollClipDisabled()` was worse (scrolled content drew over the header). Corner radii nest: well 24, cards 12 inside its 14 pt padding, tiles 20.
- **Downloads have a priority, but the queue itself cannot be manually reordered** (`DownloadKit/.../Model/QueueOrder.swift`, `DownloadManager` "Priority", `AppModel` "Priority"): the order downloads run in is `QueueOrder`: a higher `DownloadPriority` (high, normal, low) always goes first, then the earlier added (`sequence`). `DownloadManager.setPriority` is the only way to change it; it does not interrupt a running download, since the change only decides who gets the next free slot. `DownloadRecord.priority` is optional, so files from before the field existed load at normal priority. It is set from the row's context menu and the Downloads menu (a `PriorityMenu` submenu with a check mark on the priority the selection shares, shown only while at least one target is not finished) and shown in the Details pane for a download that is not finished. The list itself sorts by date added, newest first, and is not affected by priority. Dragging rows to reorder, Move to Top/Bottom and a "#" position column existed briefly (`queue-control` branch) and were removed: they added a numbered column that made the list look cluttered for a feature that mattered less than the priority itself. Named queues with their own schedule and speed limit are not built: they belong with Phase 3's scheduling.
- **Network awareness** (`DownloadKit/.../Network/`, `DownloadManager`, `AppModel.network`, `NetworkBanner`): the engine is handed a `NetworkMonitoring` (the app gives it `SystemNetworkMonitor`, an `NWPathMonitor` reduced to connected / expensive / constrained; unit tests give none, or a fake) and a `NetworkPolicy` (pause on a Personal Hotspot or cellular: off by default; respect Low Data Mode: on by default). When the connection is offline, or forbidden by the policy, `applyNetworkGate` stops the running jobs back into `.queued` (as `shutdown` does: progress is kept, and they resume from it when the block lifts), `scheduleNext` starts nothing (`networkBlock == nil` in its loop), and downloads the *user* paused stay paused. Offline can never be overridden; on an expensive or constrained connection "Download Anyway" (`overrideNetworkBlock`) lifts the block until the connection *changes* (a status that differs from the last one; a repeated report of the same status changes nothing). `load()` reads the connection before it schedules anything, because downloads that were running at the last quit resume the moment they are queued: starting them offline just to stop them again would be wasted work and a burst of failed requests. The engine reports the state on its own stream (`networkStates()`, current state first), not as a `DownloadEvent`, since it is rare and every consumer of the event enum would otherwise have to handle it. The app shows it as a banner under the toolbar, only while something is queued (an offline Mac with an empty list says nothing), and a queued row reads "Waiting for network" (`AppModel.statusText(of:)`; the Status column is wide enough for it). To look at it in a real window without touching the Mac's connection, sandbox mode reads `FETCHTHINGS_NETWORK_FILE=<file>` (`FileNetworkMonitor`): the word in the file (`offline`, `expensive`, `constrained`; anything else is online) is the network, and changing the file changes it within half a second. Checked that way: offline stops a running download at 6% and it resumes from 6% (not from zero) when the file says online; a relaunch while offline sends no request until it says online; Low Data Mode shows the banner and "Download Anyway" resumes it, and a change of connection ends that choice.
- **Speed modes** (`SpeedMode`, `SpeedModePicker`): Low, Normal and High are the global speed limit, chosen with one pop-up control at the foot of the sidebar (a `safeAreaInset` in `SidebarView`) and in the Downloads menu. Closed it is a rounded button of tinted Liquid Glass in the current mode's colour (red, yellow, green) with a chevron; opened (a `.popover(arrowEdge: .top)`, which opens upward) it lists the three modes as buttons in their own colours, the chosen one in full colour with a check mark. **Corner radii must nest**: the system popover's corners are about 20 pt on macOS 26 (measured from a screenshot: trace the border arc, the radius is where it meets the straight edge), so the rows are rounded rectangles of radius 20 - 8 (the inset around and between them) = 12 (`SpeedModeShape`); full capsules looked pinched against the popover's corners. The closed button uses the same shape. The 10 pt popover radius assumed for macOS 15 is a guess, not checked. It is hand-drawn because native menu items cannot carry colour or glass; each capsule is its own glass shape (in one container they blend). The chosen yellow uses dark text. It fits the narrowest sidebar (190 pt) in English and Turkish. The limits are Low 1024 KB/s and Normal 4096 KB/s (`SpeedMode.defaultLowKBps`/`defaultNormalKBps`, editable in Settings > Network, kept in `AppSettings` as `lowLimitKBps`/`normalLimitKBps`), High is unlimited and is the default, which matches how the app behaved before modes existed. `AppModel.selectSpeedMode` updates the setting and tells the engine. The old free-form global limit setting is gone (per-download limits in the Add sheet remain). The figures were specified as "1024" and "4096"; they are KB/s, the app's unit (about 1 and 4 MB/s).
- **Localization** uses String Catalogs: English is the source and Turkish the first translation. `App/Resources/Localizable.xcstrings` (the app), `App/Resources/ServicesMenu.xcstrings` (the "Add to FetchThings" Services item, looked up from Info.plist) and `DownloadKit/Sources/DownloadKit/Resources/Localizable.xcstrings` (the engine's messages, written by hand, read with `String(localized:bundle: .module)`). Literals passed to SwiftUI (`Text("…")`, `Button("…")`, `.help`) are localized by type and extracted by the compiler, but a plain `String` is not: anything that reaches the UI as a `String` (status names, alert titles, sidebar titles, counts, a view's `title: String` parameter) must go through `String(localized: "…")` or be a `LocalizedStringKey`/`LocalizedStringResource` (`ValueStepper.title` was once a `String` and silently stayed English). Counts use one key with a plural variation in the catalog (`"%lld downloads"`), not code that picks a singular. Whole sentences, not fragments joined in code. To add strings or a language: build, then `xcrun xcstringstool sync App/Resources/Localizable.xcstrings --stringsdata <each FetchThings.build/**/*.stringsdata>` (repeat `--stringsdata`; it lists new keys and marks removed ones stale), translate the new keys in the catalog, and for a new language add it to `CFBundleLocalizations` in `project.yml` and to all three catalogs. The engine's technical detail fragments (`why` in `unsupportedURL`, `invalidOption`, `fileSystem`...) and Foundation's HTTP status text stay English. A failed download's message is stored as text when it fails, so it keeps the language it was produced in. Check a language by launching with `-AppleLanguages "(tr)" -AppleLocale tr_TR` (this one is honoured; `-AppleInterfaceStyle` was not) and by running the app tests with `-testLanguage tr -testRegion TR`.
- **The app follows the system language by default and needs no code for it**: `CFBundleLocalizations` plus the catalogs are all `Bundle`'s language resolution needs. Settings > General > Language (`AppSettings.language`, an `AppLanguage`: `.system`, `.english`, `.turkish`) lets the user override it, the same mechanism as `-AppleLanguages` and Xcode's own "App Language" scheme setting: choosing one writes `["en"]`/`["tr"]` to the `AppleLanguages` key in the app's own preferences domain, which is only read once at launch, so the Settings picker's `onChange` offers a confirmation dialog ("Relaunch Now" / "Later") and `AppModel.relaunch()` opens a second instance (`NSWorkspace.openApplication`, `createsNewApplicationInstance = true`) before quitting this one through the normal `NSApp.terminate` path, so running transfers stop the same way a manual quit does. **`language` is kept under its own key, not read back from `AppleLanguages`**: a `UserDefaults` instance, even a throwaway suite made for one test, still falls through to the Global Domain for a key it has no entry of its own for, and `AppleLanguages` is exactly that kind of key (it is what every Mac already has the system's preferred languages in); reading it back to decide what the user chose read that leaked system value and misread the system's own preference as an app-made choice, including right after removing the override. Keeping the two keys apart also protects tests and `FETCHTHINGS_SANDBOX` runs, which already use a throwaway `UserDefaults` suite for everything `AppSettings` stores: writing `AppleLanguages` there cannot affect what language the running process actually resolves to (only the real standard domain can), which is correct — a sandboxed run must not change the installed app's language — while `language` itself still round-trips normally for the picker's own state.
- **SwiftUI gotchas found by looking at the real window** (none of them visible to unit tests): `DisclosureGroup` inside a grouped `Form` did not react to clicks or Accessibility presses, so the Add sheet's "Advanced" section is an explicit button row (`advancedHeader`); a toolbar `Toggle` exposes no title to VoiceOver (use a `Button`); `ProgressView(value: 0)` draws a nub, so `ProgressBar` is drawn by hand and reads `\.backgroundProminence` to turn white on a selected (blue) row, as does the red "Failed" text; the default zebra stripes run through the empty-state message (`.alternatingRowBackgrounds(.disabled)` when empty); after using the toolbar search field a click in the table did not take keyboard focus from it (so Delete and the arrow keys went to the field), hence the tap gesture in `MainView` that moves `@FocusState` to the table; the byte-count style spells zero as "Zero kB" (`spellsOutZero: false`); a tall `TextEditor` for the links swallowed Return (it inserted a line break, so the default button never fired), which is one reason the field is now a one-line `TextField`.
- **`DownloadManager` gets the add order from the snapshot** (`DownloadSnapshot.sequence`), not from a parallel dictionary that had to be kept in step with `snapshots`.
- **Job files keep milliseconds** (`FileJobStore` date strategy; old whole-second files are still read). With plain `.iso8601` a batch added together tied on `createdAt` after a restart and the table's tie-break (the id) scrambled its order. Milliseconds still tie for a batch added in a tight loop, so `DownloadSnapshot.sequence` (the record's add order, which the engine already used for the queue) is the second sort key, before the id.
- Tables sort on computed `DownloadSnapshot` keys (`sizeSortKey`, `progressSortKey`, …) defined in `SnapshotDisplay.swift`. Formatting follows the user's locale, so tests must not assert exact percent or date strings.

## Verifying UI work

Build, unit and integration tests are not enough for layout: the crash above and the vertical-centring bug were only visible in a real window. With **Screen Recording and Accessibility granted to the Claude app** (System Settings > Privacy & Security; the process chain is Claude.app > claude > zsh, and a small Swift probe calling `AXIsProcessTrusted()`, `CGPreflightScreenCaptureAccess()` and `CGPreflightPostEventAccess()` reports each grant without prompting) the running app can be seen and driven:
- **Screenshot one window, not the screen:** find its id with `CGWindowListCopyWindowInfo` (owner name `FetchThings`; ignore the 1470x33 menu-bar windows, pick the one taller than 100) and run `screencapture -x -o -l<id> out.png`. Window pixels are 2x its size in points.
- **Drive it with `osascript` System Events, always behind a watchdog** (e.g. `subprocess.run(..., timeout=15)`): a missing grant makes it block on a prompt on the user's screen. The app must be *frontmost* (`open`, not `open -g`) or System Events reports zero windows. Useful paths: `tell process "FetchThings" to tell window 1`; `set size to {860, 600}`; `click button 7 of toolbar 1` (Details), `button 1` (sidebar), `button 2` (Add); the table is `outline 1 of scroll area 1 of group 2 of splitter group 1 of group 1` (`select row N`), the sidebar list is `outline 1 of scroll area 1 of group 1 of splitter group 1 of group 1`. Read `AXTitle`/`AXDescription`/`AXHelp` to check what VoiceOver gets.
- **Stress the layout:** a script that randomly resizes the window (860 to 1500 wide), toggles the pane and the sidebar, selects sidebar rows and drags the sidebar divider with synthetic mouse events (`CGEvent`), checking after every step that the app still answers within 3 s and the process is alive, then `/usr/bin/log show --predicate 'process == "FetchThings" AND eventMessage CONTAINS "Update Constraints"'`. With the same seed (1) the original `.inspector` build died at step 13 both times; other seeds did not always trigger it, so use several seeds and 100+ steps.
- **Drag and Quick Look were checked with scratch tools, worth rebuilding for the next change**: a tiny AppKit "drop probe" app (a `.floating` window registered for `.fileURL`) that logs the drag's operation mask, types and the file URLs it receives, dropped onto by a *slow* synthetic drag (`CGEvent`: press, wiggle past the drag threshold, glide, hover, release; a quick 0.3 s drag started no session); `CGEvent.postToPid` for Space, arrows, Esc and Option-Space (goes to that process only, unlike System Events keystrokes; the first click into an inactive window only activates it, so click twice before expecting a selection); `CGWindowListCopyWindowInfo` with `.optionOnScreenOnly` to see whether the panel (a layer-3 window) is really showing (`.optionAll` also lists ordered-out windows); an `AXSelectedRows` setter on the outline labelled "Downloads" to select rows without a click; clicking a menu item by `click menu item … of menu "Downloads"` addressed by pid. `NSLog` from the app never reached `log show`/`log stream` (its `Logger` lines did): for temporary debugging append to a file in `/tmp` and delete it afterwards. Real files are needed for previews (a 2 s H.264 `.mov`, a JPEG and a PDF can be made with AVAssetWriter/CoreGraphics; served by `python3 -m http.server`); the mock server's random bytes have none.
- Synthetic mouse drags move the user's real pointer and the app comes to the front; do this when they are not working in the window.

Other gotchas:
- zsh shadows `log`; call `/usr/bin/log stream --info --predicate 'subsystem == "com.example.FetchThings"'`.
- Launch Services ignores apps under `/private/tmp`. To test `fetchthings://` or file opens, copy the built app somewhere ordinary, run `lsregister -f` on it, and `lsregister -u` it and delete the copy afterwards so no dev build stays registered as the scheme handler.
- **Drive only a sandboxed instance** (`open -n --env FETCHTHINGS_SANDBOX=<dir> FetchThings.app`), never the user's own copy: they often have one running from Xcode (a `DerivedData/.../FetchThings.app` process), so `pkill FetchThings`, `pgrep -f "FetchThings.app"` and "the window taller than 100pt" all match theirs too. Kill and address by the exact path of the build you launched and its PID (`first process whose unix id is <pid>`, `CGWindowListCopyWindowInfo` filtered by owner PID). Delete the sandbox folder and its `com.example.FetchThings.sandbox` preferences afterwards; the unit tests leave small `FetchThingsTestHost-*` folders in `$(getconf DARWIN_USER_TEMP_DIR)`.
- **Do not use System Events `keystroke`/`key code` for anything unattended.** They go to whatever app is frontmost. Once the sandbox app lost focus mid-run, a script typed a URL and pressed Return into the Claude chat twice; another time ⌘A plus Delete aimed at the search field emptied a whole list. - A sheet is its own window in `CGWindowList`, and macOS adds a small "Siri/dictation orb" window while a text view has focus; pick windows by size and title. Context menus are windows at layer 101 and can be captured by id. Dark mode: launch with `FETCHTHINGS_APPEARANCE=dark` (the `-AppleInterfaceStyle Dark` launch argument was ignored on this OS, and changing the system appearance is not ours to do).
- Opening the app pops a window in front of the user, who may click in it (this once looked like the app adding a download by itself; the log showed a sheet with 0 links, which only a click or ⌘N produces). ## Security invariants (keep these when changing code)

- **Secrets never touch the job store.** Cookies, custom headers and Basic-auth credentials live in `SensitiveOptions` behind the `SecretStore` protocol (in-memory in the package; the app is expected to supply a Keychain-backed one). `DownloadRecord` has no field for them. `DownloadManager.add` also moves `user:pass@` out of the URL into `basicAuth` before anything is persisted.
- **Redirects:** URLSession drops `Authorization` on *every* redirect, even same-origin. `RedirectPolicy.sanitize` restores the configured headers when the target origin equals the URL the user named, and strips every non-portable header (credentials, cookies, custom tokens) for any other origin. It also refuses non-http(s) targets. Both the prober and `SegmentTransfer` must go through it.
- **File names:** `FilenameSanitizer.sanitize` (last path component only, strips control/bidi chars, no leading dots, NFC, ≤200 bytes) → `NameAllocator` (avoids existing files, `.part` files and in-flight downloads) → `DestinationResolver.childURL` (re-verifies the result is a direct child of the download folder, also for names read back from a possibly tampered job file) → `PartFile` opens with `O_NOFOLLOW` → finishing uses `renamex_np(RENAME_EXCL)` so an existing file is never overwritten. Only `http`/`https` URLs are accepted (`RequestContext.validate` also rejects header injection and reserved headers).
- Finished files get the quarantine attribute (`applyQuarantine`, credentials stripped from the recorded origin). macOS doesn't expose the recorded data URL back through resource values, so that part is tested on the pure `quarantineProperties` function.

## Testing notes

- `MockHTTPServer` (test target) is a real HTTP/1.1 server on loopback (`NWListener`), so tests exercise the actual URLSession stack. `MockResource` models server behavior (Range, HEAD, ETag/If-Range, throttling, connection drops); handler closures inject faults. Content is deterministic per offset (`MockContent`), so any range can be verified by SHA-256.
- Its `maxConcurrentConnections` counter lags slightly behind the client, so it is fine for "at least N in parallel" checks but not for upper bounds. Assert concurrency caps by replaying `manager.events()` (see `neverRunsMoreDownloadsThanTheLimit`).
- Tests must not assert localized wording (a Turkish run of the app tests, `-testLanguage tr -testRegion TR`, fails any that do): compare with the same `String(localized:)` call, or check structure. `Formatters.speed` ends in a localized unit ("MB/s" is "MB/sn" in Turkish), so assert only the size part.
- App tests (`AppTests/`) also run a real `DownloadManager` against `TinyHTTPServer` to check the model end to end (`EngineIntegrationTests`). The developer's Mac may not be set to an English locale: don't assert localized strings, and don't assume system type data exists for common formats (Matroska, WebM and Opus have no UTType on a stock Mac, hence explicit lists in `FileCategory`).
- Speed-limit tests must use files well beyond ~1 MB (buffered head start), or they finish instantly.
- `#expect(int64Optional == 8 * 1024 * 1024 - 1)` silently evaluates false: the macro types the arithmetic as `Int`. Bind a typed `Int64` constant first.
- Timing-based tests (limits, work stealing, pause/resume byte bounds) have been stress-run under CPU load; if you add one, do the same (`yes > /dev/null` ×8 in the background) before trusting it. Mutation-check new security/resume tests by breaking the code they guard and confirming they fail.
