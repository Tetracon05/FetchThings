# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## Project

A native macOS download manager (Free Download Manager–style): multi-connection downloads, SwiftUI app, no browser integration. Decisions made: macOS 15 minimum, direct notarized distribution, App Sandbox off, custom URL scheme `downloader://` (must open a prefilled Add sheet, never start a download silently). Out of scope, but the engine should stay open to them: browser integration, torrents, yt-dlp.

**Current state:** Phases 1 and 2 are done: the engine (`DownloadKit/`, a local Swift package) and the SwiftUI app (`App/`, generated Xcode project). Phase 3 is not started: menu bar extra, Dock badge/progress, Notification Center alerts, scheduling, launch at login, app icon, polish. The bundle id `com.example.Downloader` is a placeholder and builds are ad-hoc signed; the user must set a real id, `DEVELOPMENT_TEAM` and a Developer ID before distributing (Release already enables the hardened runtime). Phases: (1) engine + tests, (2) main UI, (3) menu bar, scheduling, polish. After each phase: build, run tests, then `/code-review` and `/simplify`; run `/security-review` before finishing; report honestly what was and wasn't tested.

## Commands

All engine work happens in `DownloadKit/` (Swift 6 language mode, Xcode 27 / Swift 6.4; `Mutex` needs macOS 15). No linter or formatter is configured.

```bash
cd DownloadKit
swift build --build-tests          # library + tests; the library builds with zero warnings, keep it so
swift test                         # whole suite, ~14 s
swift test --filter DownloadIntegrationTests                 # one suite
swift test --filter resumesFromTheByteWhereAConnectionDropped # one test (matches the function name)
swift test --skip-build --filter <name>                      # re-run without rebuilding
```

Tests use Swift Testing (`@Test`, `#expect`), not XCTest.

The app is an Xcode project **generated by XcodeGen** from `project.yml` (installed via Homebrew). Edit `project.yml`, not the `.xcodeproj`, and re-run `xcodegen generate` whenever files are added or removed under `App/` or `AppTests/`.

```bash
xcodegen generate
xcodebuild -project Downloader.xcodeproj -scheme Downloader -destination 'platform=macOS' build
xcodebuild -project Downloader.xcodeproj -scheme Downloader -destination 'platform=macOS' test
xcodebuild ... test -only-testing:DownloaderTests/AppModelTests   # one suite
```

Add `-derivedDataPath <dir>` to keep build output out of `~/Library`. After deleting or renaming a file under `App/` or `AppTests/`, run `xcodegen generate` again before building: the committed project lists files explicitly, and a stale one fails to build (or worse, runs a stale test bundle). The app tests are hosted inside the app and print harmless `linkd ... autoShortcut` connection errors; ignore them.

## Engine architecture (`DownloadKit/Sources/DownloadKit`)

Data flow: `DownloadManager` (actor: queue, concurrency cap, global limiter, persistence, event stream) owns one `DownloadJob` (actor) per download. A job runs probe → transfer → verify → finalize and reports `JobReport`s back through a closure. The transfer itself runs in non-isolated tasks and is only *sampled* by the job's tick loop (about 4 Hz), never driven per chunk.

- **One connection is the 1-segment case.** `TransferMode.segmented` (server gave a size and honors ranges) uses `SegmentedDownloader` + `SegmentScheduler`; `.single` uses `SingleDownloader` (plain GET, not resumable, restarts from zero). A server that advertises ranges but answers 200 makes the job throw `rangeNotHonored` and fall back to `.single`; a changed ETag/size makes it throw `resourceChanged` and restart (max 2 times).
- **`SegmentTransfer` = one request, one `URLSession`.** A session per transfer is deliberate: over HTTP/2/3, requests sharing a session are multiplexed onto one TCP connection, which would silently defeat multi-connection. Chunks are `pwrite`n from the delegate queue straight into the shared `PartFile` (no actor hop). Speed limiting suspends the `URLSessionDataTask`; URLSession and the kernel buffer roughly the first MB ahead of that, so limits are accurate on large transfers but small files finish faster than the nominal rate.
- **`SegmentScheduler` invariant (the core of resume correctness):** per segment, `received` (committed, on disk, the only value persisted) trails `reserved` (a write cursor). Workers `reserve → pwrite → commit`. Work stealing (an idle slot splits the segment with the most unreserved bytes left) only takes bytes beyond `reserved`, so no byte is written twice. Resume points always come from `received`. `SegmentedDownloader` counts an attempt against the retry budget only if the segment made no progress.
- **Probe (`Prober`):** HEAD first; range support is only believed after `Accept-Ranges: bytes`, otherwise a `Range: bytes=0-0` GET settles it (HEAD is often rejected, and many servers honor ranges without saying so). Requests send `Accept-Encoding: identity`; any `Content-Encoding` disables ranges and drops the size.
- **Manager ordering rules** (`DownloadManager.handle`): update the snapshot, broadcast, and hand the record to the store *before the first suspension*, so a job's reports keep their order. `runningIDs` is mutated synchronously before `await job.start()` so concurrent `scheduleNext()` passes can't exceed the concurrency limit; `start()` returns `false` if the job is no longer queued and the manager then gives the slot back. The manager's snapshot can lag the job, so `pause()` never trusts it: it calls `job.stop(to: .paused)`, which handles running, starting and queued jobs. After `shutdown()` nothing may start (`isShutDown`), otherwise a job stopped back to `.queued` is immediately restarted.
- **Secrets that cannot be read fail the download.** `DownloadRecord.hasSecrets` remembers that a download was added with cookies, headers or credentials; if the `SecretStore` cannot return them later, the job fails with `credentialsUnavailable` before any request, instead of downloading unauthenticated (which could save a login page as the file).
- **Job persistence:** one JSON file per download (`FileJobStore`, dir 0700, files 0600), checkpointed every `checkpointInterval` and on every state change. On `load()`, records left in a running state go back to `.queued` (auto-resume). Removing an unfinished download always deletes its `.part` file.
- **Never trust saved progress blindly.** The `.part` file is preallocated to full size, so its length says nothing about what is in it. A resume only keeps progress if `SegmentPlanner.isValidPlan` accepts the saved segments (a bad list would otherwise trap in `SegmentScheduler.init`) and the part file's size equals the total; otherwise it restarts. Completion is checked by counting received bytes, not file size. Checkpoints snapshot the counts *before* `fsync`ing the part file (`Downloader.flush`), so a checkpoint may lag the disk but never lead it. A `.single` download has nothing to resume (`downloadedBytes` is 0 until completed).
- **Errors:** `DownloadError.isRetryable` decides retry vs fail (408/425/429/5xx except 501/505, and transient `URLError`s retry; other 4xx, disk, checksum, path errors don't). `DownloadError.map` turns `URLError.cancelled` into `CancellationError`, which means "stopped by caller", never "failed".

## App architecture (`App/Sources`)

- **`AppModel`** (`@MainActor @Observable`) is the single source of truth for the window. It talks to the engine only through the `DownloadEngine` protocol (`DownloadManager` conforms; tests use `FakeEngine`). A task that is *not* on the main actor drains the engine's event stream into `EventInbox` (newest event per download, lock-protected), and the main actor applies it every 200 ms (`flushEvents`). That bounds memory whatever the UI is doing and keeps the views from refreshing on every progress tick. `visibleDownloads` (sidebar filter, search, sort) and the sidebar `counts` are recomputed only when the data or a filter changes.
- **`selection` is always a subset of `visibleDownloads`.** `recomputeVisible` prunes it, and every action (pause, remove, reveal, the toolbar state) works on the visible selection only. Without that, filtering or searching left hidden rows selected and the Remove button deleted downloads the user could not see.
- **Removing goes through `requestRemoval`**, which asks first when it would delete partly downloaded data (`PendingRemoval`, shown as a confirmation dialog). The app never asks the engine to delete finished files; "Remove and Move File to Trash" calls `FileManager.trashItem` itself (`AppModel.trash`, replaceable in tests). There is deliberately no global ⌘⌫ shortcut (it would fire while typing in a text field); Delete works through `.onDeleteCommand` on the table.
- **Start-up order matters:** `AppModel.start()` (called from `applicationDidFinishLaunching`, not from a view) applies the concurrency and speed limits *before* `engine.load()`, because loading auto-resumes downloads immediately. `onCompleted` fires for a download that finishes during this session even if its whole life fell between two refreshes; ones restored as already finished do not fire it.
- **Numbers typed by users are clamped** (`SpeedLimit`, `AppSettings`): KB/s x 1000 overflowed `Int64` and crashed on every launch when a huge value was persisted.
- **Links from outside only propose downloads.** `downloader://add?url=…`, dropped or opened `.txt` files, dropped or pasted text, Services and clipboard offers all end in `presentAddSheet`, and only the sheet's Add button calls the engine. Keep it that way: any web page can trigger a `downloader://` link. Non-http(s) links are filtered in `AppModel.links(in:)` and again by `LinkParser`.
- **Single `Window` scene, not `WindowGroup`**, so opening a link or file with the app does not spawn another window. Closing that window leaves the app running with the window retained but hidden, and SwiftUI then reports `canBecomeMain == false` for it, so `MainWindow.showIfHidden` finds it by its scene id (`MainWindow.sceneID`) and is called for link opens, Dock reopen and the Services item; otherwise the Add sheet (which lives in that window) would be invisible. URL and file opens arrive in `AppDelegate.application(_:open:)`, which is also where Dock-icon drops land; text cannot be dropped on a Dock icon, so the "Add to Downloader" Service (`NSServices` in `project.yml`, `ServicesProvider`) covers it. `AppDelegate.applicationShouldTerminate` stops the transfers (`AppModel.shutdown`) before quitting, but `TerminationGate` gives up waiting after 8 seconds so a stuck shutdown cannot block quitting.
- **Storage:** job files in `~/Library/Application Support/<bundle id>/Jobs`, secrets in the login keychain (`KeychainSecretStore`), preferences in `UserDefaults` (`AppSettings`, values clamped on load). When the app hosts unit tests (`AppEnvironment.isRunningTests`) it uses a temp job folder, an in-memory secret store and a throwaway defaults suite, so tests never touch real data.
- `Info.plist` (generated from `project.yml`) carries the pieces that must stay in sync with code: the `downloader` URL scheme, `NSAllowsArbitraryLoads` (plain http downloads), the `.txt` document type and the Services entry.
- The clipboard watcher is opt-in and uses `NSPasteboard.detectedPatterns` (macOS 15.4+) to check for a web address *without reading the contents*, then reads only on a match; before 15.4 it reads directly.
- Tables sort on computed `DownloadSnapshot` keys (`sizeSortKey`, `progressSortKey`, …) defined in `SnapshotDisplay.swift`. Formatting follows the user's locale, so tests must not assert exact percent or date strings.

## Verifying UI work without a display

Screenshots and Accessibility scripting are not available in this environment (`screencapture` fails, `osascript` System Events blocks on a permission prompt that appears on the user's screen; do not run it). What works: build, unit and integration tests, launching the app, and reading its `os.Logger` output (`subsystem com.example.Downloader`). Gotchas:
- zsh shadows `log`; call `/usr/bin/log stream --info --predicate 'subsystem == "com.example.Downloader"'`.
- Launch Services ignores apps under `/private/tmp`. To test `downloader://` or file opens, copy the built app somewhere ordinary, run `lsregister -f` on it, and `lsregister -u` it and delete the copy afterwards so no dev build stays registered as the scheme handler.
- Opening the app pops a window in front of the user, who may click in it (this once looked like the app adding a download by itself; the log showed a sheet with 0 links, which only a click or ⌘N produces). Use `open -g -j` to keep it in the background when driving it from a script. Opened links still order a hidden main window to the front but do not activate the app, so `-g` keeps working.

## Security invariants (keep these when changing code)

- **Secrets never touch the job store.** Cookies, custom headers and Basic-auth credentials live in `SensitiveOptions` behind the `SecretStore` protocol (in-memory in the package; the app is expected to supply a Keychain-backed one). `DownloadRecord` has no field for them. `DownloadManager.add` also moves `user:pass@` out of the URL into `basicAuth` before anything is persisted.
- **Redirects:** URLSession drops `Authorization` on *every* redirect, even same-origin. `RedirectPolicy.sanitize` restores the configured headers when the target origin equals the URL the user named, and strips every non-portable header (credentials, cookies, custom tokens) for any other origin. It also refuses non-http(s) targets. Both the prober and `SegmentTransfer` must go through it.
- **File names:** `FilenameSanitizer.sanitize` (last path component only, strips control/bidi chars, no leading dots, NFC, ≤200 bytes) → `NameAllocator` (avoids existing files, `.part` files and in-flight downloads) → `DestinationResolver.childURL` (re-verifies the result is a direct child of the download folder, also for names read back from a possibly tampered job file) → `PartFile` opens with `O_NOFOLLOW` → finishing uses `renamex_np(RENAME_EXCL)` so an existing file is never overwritten. Only `http`/`https` URLs are accepted (`RequestContext.validate` also rejects header injection and reserved headers).
- Finished files get the quarantine attribute (`applyQuarantine`, credentials stripped from the recorded origin). macOS doesn't expose the recorded data URL back through resource values, so that part is tested on the pure `quarantineProperties` function.

## Testing notes

- `MockHTTPServer` (test target) is a real HTTP/1.1 server on loopback (`NWListener`), so tests exercise the actual URLSession stack. `MockResource` models server behavior (Range, HEAD, ETag/If-Range, throttling, connection drops); handler closures inject faults. Content is deterministic per offset (`MockContent`), so any range can be verified by SHA-256.
- Its `maxConcurrentConnections` counter lags slightly behind the client, so it is fine for "at least N in parallel" checks but not for upper bounds. Assert concurrency caps by replaying `manager.events()` (see `neverRunsMoreDownloadsThanTheLimit`).
- App tests (`AppTests/`) also run a real `DownloadManager` against `TinyHTTPServer` to check the model end to end (`EngineIntegrationTests`). The developer's Mac may not be set to an English locale: don't assert localized strings, and don't assume system type data exists for common formats (Matroska, WebM and Opus have no UTType on a stock Mac, hence explicit lists in `FileCategory`).
- Speed-limit tests must use files well beyond ~1 MB (buffered head start), or they finish instantly.
- `#expect(int64Optional == 8 * 1024 * 1024 - 1)` silently evaluates false: the macro types the arithmetic as `Int`. Bind a typed `Int64` constant first.
- Timing-based tests (limits, work stealing, pause/resume byte bounds) have been stress-run under CPU load; if you add one, do the same (`yes > /dev/null` ×8 in the background) before trusting it. Mutation-check new security/resume tests by breaking the code they guard and confirming they fail.
